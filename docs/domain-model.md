# Предметная модель первой версии

Модель развивает [согласованную первую версию](first-version.md), сохраняя обязательную выдачу и отзыв GitHub-доступов. Термины определены в [DOMAIN.md](../DOMAIN.md). Ответственность модулей принята 4 ноября 2026 года после [исследования учебного проекта](research/2026-11-04-ai-first-platform-issue-1-pr-7-pr-9.md) и поручения перенести рекомендации. Открытые продуктовые вопросы перечислены отдельно.

## Согласованные отношения и правила

### Сотрудник, приглашение и роль

- Платформа обслуживает одну компанию и использует две роли: сотрудник и администратор.
- Администратор создаёт одноразовое приглашение с ограниченным сроком действия, передаёт ссылку сотруднику и может отменить её.
- Принятие приглашения создаёт учётную запись; затем сотрудник может входить повторно. Приглашение само по себе не даёт доступа к проектам.
- Администратор управляет проектами, назначениями и отключением сотрудников. Порядок первоначального назначения администратора и его доступ к рабочим сведениям проектов требуют уточнения.
- Сотрудник подтверждает связь своей учётной записи платформы с собственной учётной записью GitHub.

### Проекты, репозитории и назначения

- Проект объединяет один или несколько существующих GitHub-репозиториев и общий набор инструкций.
- Сотрудник может иметь несколько назначений на проекты; один репозиторий может входить в несколько проектов.
- Назначение относится ко всему проекту. Для нового назначения сведения проекта открываются после подтверждения выдачи прав ко всем его репозиториям.
- Частично выполненная выдача не считается завершённым подключением. Уже выданные права учитываются при повторе и при отключении.
- При удалении назначения сведения проекта сразу закрываются. GitHub-права на общий репозиторий сохраняются, если он требуется другим сохраняющимся назначениям сотрудника.
- Доступ к общему репозиторию не открывает сведения чужих проектов и их общие инструкции: для каждого проекта проверяется собственное назначение.
- Изменение состава проекта запускает обновление GitHub-доступов назначенных сотрудников. Ошибки и незавершённые изменения видны администратору.

### Разрешения платформы и GitHub-права

- Разрешение платформы определяет, какие действия и сведения доступны сотруднику. GitHub-права определяют доступ к внешним репозиториям. Один вид разрешения не заменяет другой.
- Пилот ограничен одной подготовленной GitHub-организацией. Независимые способы доступа, препятствующие полному отзыву, устраняются при подключении репозиториев администратором.
- Сотрудник получает единый доступ разработчика: чтение, отправку изменений в рабочие ветки и создание pull request с сохранением действующих ограничений GitHub.
- Полное отключение не считается завершённым при сохранившемся независимом доступе. Способ проверки этой гарантии требует исследования GitHub.

### Инструкции и подготовка окружения

- Администратор редактирует в платформе один общий набор инструкций проекта: репозитории, предварительные условия, подготовку, проверки готовности и правила работы.
- Локальные правила репозиториев остаются в Git; они не заменяют общий набор инструкций. Способ получения локальных правил и разрешения противоречий ещё не выбран.
- Изменённые инструкции доступны при следующем запросе; автоматического перезапуска подготовки на компьютерах нет.
- Сотрудник заранее устанавливает выбранного агента и базовые инструменты и получает секреты. Агент выполняет шаги подготовки одного описанного варианта окружения и проверки, сообщает результаты и препятствия.
- Успех подготовки определяется указанными проверками. После устранения препятствия подготовку можно повторить.

### Подключение агента

- Подключение принадлежит сотруднику. Агент получает сведения в пределах актуальных прав владельца и не получает административных полномочий.
- Сотрудник подключает агента, сотрудник и администратор могут отозвать подключение без отключения самого сотрудника. После отзыва возможно новое подключение.
- Для выдачи данных необходимы действующие учётная запись, подключение и разрешение владельца на запрошенные сведения.
- Один поддерживаемый тип агента не определяет число одновременных подключений. Несколько независимо отзываемых подключений — вопрос для отдельного согласования.

### Отключение сотрудника

- Одно действие администратора блокирует новые входы, действующие сеансы платформы и все подключения агента; запускается отзыв GitHub-доступов.
- После блокировки новые обращения сотрудника и агента не получают сведения через платформу. Проверка опирается на текущее состояние, а не только на права при первоначальном входе.
- При сбое GitHub блокировка платформы сохраняется, операция остаётся незавершённой и повторяется. Администратор видит оставшиеся доступы, причины и может повторить действие.
- Полный успех показывается после подтверждения отзыва внешних доступов. Уже скачанные код и инструкции не стираются.
- Сохранение учётной записи и порядок возвращения сотрудника пока не согласованы. Автоматическое восстановление старых прав не следует из возможности повторного подключения агента.

## Пять модулей обязательной поставки

| Модуль | Владеет | Интерфейс в предметных терминах |
| --- | --- | --- |
| Сотрудники | Учётные записи, приглашения, вход, подтверждение личности, активность учётной записи | Пригласить; принять или отменить приглашение; войти; блокировать учётную запись; определить активность |
| Проекты | Состав проектов, связи с репозиториями, общий набор инструкций, предоставление разрешённого содержимого | Создать или изменить проект; получить состав репозиториев; изменить инструкции; предоставить разрешённые сведения |
| Доступ | Назначения, административные полномочия, проверки разрешений, сквозные операции изменения доступа, состояния и повторы | Назначить проект; удалить назначение; проверить разрешение; определить доступные проекты; отключить сотрудника; получить состояние или повторить операцию |
| Подключения агентов | Владелец подключения, его действительность и отзыв | Подключить агента от своего имени; определить владельца действующего подключения; отозвать подключение или все подключения сотрудника |
| Интеграции | Связь учётных записей с GitHub, выполнение внешних изменений и подтверждённый результат | Связать GitHub-аккаунт; выдать или отозвать доступ к репозиторию; подтвердить результат внешней операции |

«Доступ» учитывает факты других модулей, сохраняя за ними владение этими фактами. «Проекты» предоставляют содержимое после проверки разрешения; «Интеграции» выполняют внешние изменения по основаниям, определённым «Доступом». Изменение административных полномочий проверяется «Доступом»; правила назначения первого и защиты последнего администратора пока открыты.

Владелец разрешений и компромисс описаны в [ADR-0001](adr/0001-platform-access-ownership.md); владелец сквозных операций — в [ADR-0002](adr/0002-access-change-orchestration.md). Пять модулей задают ответственность, сохраняя открытыми стек и технический способ взаимодействия.

## Сквозные сценарии

| Сценарий | Ответственность и признак завершения |
| --- | --- |
| Приглашение и вход | «Сотрудники» создают приглашение, принимают его, создают учётную запись и подтверждают личность при входе. Назначения ведёт «Доступ»; вход сам по себе не открывает все проекты. |
| Назначение проекта | «Доступ» проверяет полномочия администратора и ведёт операцию; «Проекты» определяют состав репозиториев, «Интеграции» выдают внешние права. Сведения нового назначения открываются после подтверждения всех необходимых прав. |
| Чтение сотрудником | «Доступ» проверяет активность и разрешение; «Проекты» предоставляют разрешённые сведения. |
| Чтение агентом | «Подключения агентов» подтверждают владельца и действительность подключения; применяются проверки «Доступа» с учётом текущего состояния владельца; «Проекты» предоставляют сведения. |
| Изменение репозиториев | «Проекты» меняют состав, «Доступ» ведёт обновление назначений и необходимых внешних прав, «Интеграции» выполняют изменения. Незавершённые обновления видны администратору. |
| Удаление назначения | «Доступ» сразу закрывает сведения проекта и вычисляет, какие внешние права больше не нужны с учётом остальных назначений. «Интеграции» подтверждают отзыв этих прав. Подключение агента и другие назначения сохраняются. |
| Полное отключение | «Доступ» ведёт операцию: сначала блокирует учётную запись через «Сотрудников», затем доводит до завершения отзыв назначений, всех подключений и внешних прав. Блокировка сохраняется при ошибке любого последующего шага. |
| Повтор операции | «Доступ» проверяет актуальность оснований, учитывает подтверждённые результаты и повторяет необходимые действия. Повтор устаревшей выдачи не восстанавливает отменённый доступ. |

Внешний запрос на назначение или отключение не требует от вызывающей стороны самостоятельно повторять шаги разных модулей. Порядок действий и ошибки скрыты за интерфейсом «Доступа». Администратор получает состояние операции, оставшиеся действия и причины; для назначений и запуска отключения сохраняются инициатор и время.

## Проверка будущей реализации

Критерий поставки остаётся в [первой версии](first-version.md). При реализации проверки поведения размещаются в `tests/` и проходят через интерфейсы модулей. Особое внимание требуется общим репозиториям без раскрытия чужих проектов, запрету новых выдач после блокировки, частичной выдаче и отзыву, актуальности повторов и сохранению блокировки при ошибках GitHub. Это требования к будущим проверкам; приложение и автоматические проверки поведения пока отсутствуют.
