# Первая версия платформы

Согласованные границы первой версии на основе [требований заказчика](requirements.md).

Первая версия помогает подключить разработчика и его агента к проектам компании, подготовить рабочее окружение и закрыть доступы при уходе сотрудника.

## Обязательные сценарии и границы

1. **Границы первой версии.** Платформа обслуживает одну компанию. Пилот работает с одной заранее подготовленной GitHub-организацией. Поддерживается один выбранный командой тип агента разработчика. Конкретный агент, интерфейсы, способ подключения и технические решения выбирает команда.

2. **Сотрудники и приглашения.** Администратор создаёт приглашение и самостоятельно передаёт ссылку сотруднику. Приглашение одноразовое, имеет срок действия и может быть отменено. Сотрудник принимает приглашение, создаёт учётную запись и затем может входить повторно.

   Используются две роли: администратор и сотрудник. Администратор управляет приглашениями, проектами, назначениями и отключением сотрудников. Сотрудник работает с назначенными проектами и подключает своего агента.

3. **Проекты и инструкции.** Администратор создаёт проект, добавляет существующие GitHub-репозитории и редактирует инструкции. Проект может объединять несколько репозиториев; один репозиторий может входить в несколько проектов.

   Для проекта хранится один общий набор инструкций: состав репозиториев, предварительные условия, подготовка окружения, проверки готовности и правила работы. Инструкции доступны назначенному сотруднику и его агенту. Правила, уже находящиеся в репозиториях, сохраняются на своих местах.

   Новые инструкции доступны при следующем запросе. Изменение состава репозиториев запускает обновление доступов всех назначенных сотрудников. Подготовка окружения на их компьютерах автоматически не перезапускается.

4. **Назначение доступа.** Администратор назначает сотруднику один или несколько проектов. Назначение даёт доступ к проекту целиком, включая все его репозитории.

   Сотрудник использует собственную учётную запись GitHub и подтверждает её связь с учётной записью платформы. Доступ позволяет читать код, отправлять изменения в рабочие ветки и создавать pull request. Существующие ограничения GitHub продолжают действовать.

   Сначала платформа выдаёт доступы ко всем репозиториям нового назначения, затем открывает сведения проекта сотруднику и агенту. До завершения выдачи операция отображается как незавершённая.

   Доступы складываются по проектам. При удалении назначения общий репозиторий остаётся доступен, если он нужен сотруднику для другого назначенного проекта.

5. **Интеграция с GitHub.** Подключение внешних сервисов выделено в отдельный модуль интеграций. В первой версии реализуется только GitHub.

   Подготовку организации выполняет администратор. Для подключаемых репозиториев платформа должна иметь возможность управлять доступами сотрудников. Независимые способы доступа, мешающие полному отзыву, должны быть устранены при подключении. Автоматический перенос произвольной существующей системы прав не входит в первую версию.

   Платформа не должна показывать успешное полное отключение, если доступ сотрудника сохраняется через независимое назначение.

6. **Подключение агента.** Сотрудник самостоятельно подключает агента. Агент получает только проекты, репозитории и инструкции, доступные этому сотруднику. Подключение агента не даёт административных полномочий.

   Сотрудник и администратор могут отозвать подключение агента, сохранив доступ самого сотрудника. После отзыва сотрудник может подключить агента заново.

7. **Подготовка рабочего окружения.** Для каждого проекта поддерживается один заранее описанный вариант локального окружения. Сотрудник заранее устанавливает выбранного агента и базовые инструменты, а также самостоятельно получает необходимые секреты.

   Агент получает репозитории, выполняет описанные шаги подготовки, проверяет доступы и запускает указанные проверки готовности. Он сообщает результат каждого шага и конкретные препятствия: отсутствующий инструмент, секрет, недоступный репозиторий или ошибку команды. После устранения препятствия подготовку можно запустить повторно.

   Сценарий завершён, когда предусмотренные проверки готовности успешно выполнены.

8. **Удаление назначения и отключение сотрудника.** При удалении сотрудника из проекта сведения этого проекта сразу становятся недоступны ему и его агенту. Платформа отзывает GitHub-доступы, которые больше не нужны для других назначенных проектов.

   Полное отключение сотрудника одним действием администратора блокирует новые входы, действующие сеансы платформы и все подключения его агента. Одновременно запускается отзыв доступов ко всем управляемым репозиториям.

   Отключение прекращает получение данных через платформу. Уже скачанный код и ранее полученные инструкции могут оставаться на компьютере; удалённое стирание данных не входит в первую версию.

9. **Сбои и контроль операций.** Выдача или отзыв GitHub-доступов могут завершиться частично. Платформа учитывает уже выданные права при повторе операции и отключении сотрудника.

   Если GitHub недоступен, сотрудник остаётся заблокированным в платформе, а отключение отображается как незавершённое. Отзыв повторяется до подтверждения результата; администратор видит оставшиеся доступы, причины ошибок и может повторить операцию. Успех показывается после подтверждения отзыва в GitHub.

   Администратору доступны списки сотрудников и проектов, назначения и состояния операций выдачи, обновления и отзыва доступов. Сохраняется, кто и когда изменил назначения или запустил отключение.

10. **Критерий готовности.** На реальном проекте с несколькими GitHub-репозиториями администратор и новый сотрудник проходят весь цикл: приглашение, создание учётной записи, привязку GitHub, назначение проекта, подключение агента и подготовку окружения. После отключения сотрудник теряет доступ к платформе и репозиториям, а новые запросы агента за данными отклоняются.

    Цикл выполняется предусмотренными средствами платформы, без ручного редактирования базы или исправления доступов разработчиком платформы. Проверяются также общие репозитории нескольких проектов, частичная выдача прав и незавершённый отзыв при сбое GitHub.

## За пределами первой версии

- Несколько компаний, самостоятельная регистрация, автоматическая отправка приглашений и корпоративный единый вход.
- Команды, дополнительные роли, отдельные права на репозитории, режим «только чтение» и управление правилами слияния.
- Создание репозиториев, перенос кода, автоматический перенос существующей системы прав и дополнительные интеграции.
- Персональные инструкции, наследование правил и общий каталог скиллов.
- Несколько типов агентов, агент компании, поиск по документации и подбор задач.
- Трекер задач, облачное выполнение, песочницы и параллельные агенты.
- Хранилище и автоматическая выдача секретов, универсальная настройка компьютеров и установка базовых инструментов средствами платформы.
- Учёт расходов на модели, расширенная аналитика, отдельная система аудита, оценка качества агентов, управление релизами и эксплуатацией.
